# Обоснование конфигурации облачной инфраструктуры «Будущее 2.0»

## 1. Выбор облачного провайдера — Yandex Cloud

Компания «Будущее 2.0» работает в России и оказывает медицинские и финансовые услуги, для которых действуют требования 152-ФЗ (персональные данные) и требования ЦБ РФ (финтех). Yandex Cloud располагает ЦОДами на территории РФ, сертифицированными по ГОСТ Р 57580, что закрывает регуляторные требования без организации трансграничной передачи данных.

## 2. Выбор ресурсов и их параметры

### 2.1 Сеть (VPC + подсети + NAT Gateway)

В Task2 определены шесть бизнес-доменов: медицинский, финтех, управление клиниками, ИИ-сервисы, партнёрские системы, аналитика данных. На уровне сетевой инфраструктуры домены изолируются **логически** (отдельные Kafka-топики, префиксы в Object Storage, пространства имён в Dremio), а не отдельными подсетями для каждого из шести доменов. подсети сгруппированы по **функциональному назначению инфраструктурных сервисов** — это типовая практика, которая сокращает количество правил безопасности и упрощает маршрутизацию, сохраняя изоляцию на уровне приложений.

| Подсеть       | CIDR        | Зона          | Размещаемые сервисы                    | Обслуживаемые домены (Task2)                   |
|---------------|-------------|---------------|----------------------------------------|------------------------------------------------|
| management    | 10.0.0.0/24 | ru-central1-a | Мониторинг, jump host                  | Все домены (операционный контроль)             |
| data-platform | 10.0.1.0/24 | ru-central1-a | Kafka (немедицинские), Nessie          | Финтех, клиники, партнёры, аналитика данных    |
| analytics     | 10.0.2.0/24 | ru-central1-b | Dremio, Airflow                        | Аналитика данных, финтех, управление клиниками |
| ai            | 10.0.3.0/24 | ru-central1-b | ИИ-сервисы                             | ИИ-сервисы                                     |
| medical       | 10.0.4.0/24 | ru-central1-a | Kafka (медицинские), Nessie (medical)  | Медицинский домен — **только ИИ-сервисы**      |

Подсеть `medical` и её `sg-medical` образуют **сетевой барьер** для медицинских данных: группа безопасности разрешает порты 9092 (Kafka) и 19120 (Nessie) исключительно из `ai_cidr` (10.0.3.0/24). Аналитическая подсеть (Dremio, Airflow) физически не может установить соединение с медицинским брокером или каталогом — это выполняет требование ФЗ-323 и 152-ФЗ на уровне сетевого периметра.

**NAT Gateway** (shared egress) заменяет NAT-инстанс: управляется платформой, не требует ручной поддержки и масштабируется автоматически. Все ВМ в частных подсетях получают исходящий доступ в интернет (для обновлений пакетов, docker pull и т.п.) без публичных IP, что сокращает поверхность атаки.

**Группы безопасности** настроены по принципу минимальных привилегий: только необходимые порты, только между нужными подсетями.

### 2.2 Виртуальные машины

| ВМ          | vCPU | RAM   | Дополнительный диск | Обоснование                                                                                                                                                                  |
|-------------|------|-------|---------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| monitoring  | 2    | 4 ГБ  | —                   | Grafana + Prometheus — небольшая нагрузка; нет смысла переплачивать                                                                                                          |
| kafka       | 4    | 16 ГБ | 500 ГБ SSD          | Kafka-брокер требует быстрый диск для журнала (log segments) и достаточно RAM для page cache. 500 ГБ покрывает хранение событий с retention 7 дней при нагрузке всех доменов |
| nessie      | 2    | 4 ГБ  | —                   | Apache Nessie — REST-сервер каталога Iceberg; нагрузка на CPU и память невысокая                                                                                             |
| dremio      | 8    | 32 ГБ | 200 ГБ SSD          | Dremio выполняет распределённые SQL-запросы в памяти. Достаточный объём RAM критичен для производительности; 200 ГБ SSD используется как локальный кэш (reflection store)    |
| airflow     | 4    | 8 ГБ  | —                   | Airflow-планировщик + воркеры; нагрузка умеренная, воркеры можно масштабировать горизонтально отдельно при росте DAG-нагрузки                                                |

Для всех ВМ выбрана платформа `standard-v3` (Intel Ice Lake) — актуальное поколение процессоров в Yandex Cloud с хорошим соотношением цена/производительность и поддержкой AVX-512 (полезно для ИИ-нагрузок в будущем).

Загрузочные диски — `network-ssd`; данные для Kafka и Dremio вынесены на отдельные диски, чтобы можно было изменить их размер независимо от ВМ и не потерять данные при пересоздании ВМ.

### 2.3 Объектное хранилище (Data Lake)

Yandex Object Storage (S3-совместимое) используется как единое озеро данных вместо MinIO. Это управляемый сервис: не нужно администрировать процессы, резервное копирование и замену дисков. Включено версионирование объектов — защита от случайного удаления файлов Parquet/Iceberg.

## 3. Компоненты, управляемые Terraform, и развёртываемые вручную

### Terraform (IaC)

- VPC, подсети, таблицы маршрутизации
- NAT Gateway
- Группы безопасности
- Статический публичный IP для monitoring-node
- Дополнительные диски (Kafka, Dremio)
- Виртуальные машины (monitoring, kafka, nessie, dremio, airflow)
- Bucket объектного хранилища

### Вручную

| Компонент                | Причина                                                                                                                               |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------|
| Генерация SSH-ключей     | Приватный ключ не должен появляться в коде или state-файле                                                                            |
| Статические ключи для S3 | Создаются через IAM одноразово; ротация — отдельный процесс                                                                           |
| DNS-записи               | Внешний DNS управляется не в этом проекте                                                                                             |
| SSL/TLS сертификаты      | Выпускаются через Let's Encrypt или PKI организации                                                                                   |
| Установка ПО на ВМ       | Конфигурация приложений (Kafka topics, Airflow connections, Dremio sources) — задача Configuration Management (Ansible), не Terraform |
| Grafana dashboards       | Живут в Git отдельно и деплоятся как JSON-конфигурация                                                                                |

## 4. Декларативный подход и IaC

### Почему декларативный подход

В императивном подходе инженер описывает **как** создать ресурс (последовательность вызовов API). В декларативном — **что** должно существовать. Terraform транслирует декларацию в план действий, вычисляя diff между желаемым и текущим состоянием. Это устраняет ошибки «забыл откатить шаг» и позволяет безопасно переприменять конфигурацию.

### IaC и воспроизводимость

Конфигурация в Git является единственным источником истины об инфраструктуре. Любой инженер команды может развернуть точную копию окружения командой `terraform apply`. Это даёт:

- **Паритет сред**: dev, staging и prod строятся из одного кода с разными `terraform.tfvars`, что исключает ситуацию «у меня работает, в проде нет».
- **Аудит изменений**: история Git показывает, кто, когда и зачем изменил инфраструктуру.
- **Disaster Recovery**: потеря облачного окружения устраняется повторным `terraform apply`, а не многочасовым ручным восстановлением.

### IaC и масштабируемость

При подключении нового домена (например, фармацевтический партнёр из роадмапа Task3) достаточно добавить новый блок подсети и ВМ в `main.tf` и передать PR на ревью. Terraform сам определит, что создать, и не затронет существующие ресурсы. Горизонтальное масштабирование Kafka или Dremio реализуется изменением одной переменной и `terraform apply` — без ручных операций в консоли облака.

### Связь с бизнес-целями

Из роадмапа Task3: этап «Подготовка инфраструктуры в облаке» запланирован на Q3 2026 и является блокером для всех последующих этапов миграции доменов. IaC позволяет подготовить инфраструктуру быстро и без ошибок, сокращая time-to-market для портала самообслуживания, и обеспечивает воспроизводимость при масштабировании под новых партнёров (фармацевтика, электроника).
